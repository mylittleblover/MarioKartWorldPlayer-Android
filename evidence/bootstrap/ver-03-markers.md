## 1. 之前卡住的原因

旧实现找错了两处：

1. **记录起点算错**：`+20` 不是"记录表起始"，而是**标记段的偏移量**。真正的记录从 `+20 + 4` 开始
2. **步长算错**：以为是 12 字节，实际是 **16 字节**

修正后，Coaster 的 7 条记录立刻呈现完美结构。

---

## 2. 已验证的布局

```
AMTA 头
  +20   u32   标记段偏移 sectionOffset

在 sectionOffset 处：
  +0    u32   标记数量 count
  +4    记录 × count，每条 16 字节：
          +0   u32  index          0..count-1，严格按位序
          +4   u32  markerId       全局唯一标识
          +8   u32  sourceSamplePosition   源采样帧位置
          +12  u32  恒为 0
```

## 4. 交叉印证：229/229 位置一致（非独立权威）

`triggers.md` 是**分析产物**，不是游戏内原生数据。它能做的是**交叉印证**，不能定义正确性。

**把 229 个位置拿去 BARS 标记表里找：**

```
triggers.md positions: 229
present in BARS marker tables: 229
```

**100% 命中。**

这个结果说明什么、不说明什么：

| 说明 | 不说明 |
|---|---|
| 两个独立分析路径得到同一批采样位置 | 这些位置在游戏里**真的**被用来切 Outro |
| BARS 位置字段不是垃圾数据 | 位置对应哪个 `OutroNN` 名字 |
| 位置是真实源采样帧坐标 | 触发时机、条件、优先级 |

## 5. `markerId` 不是 Outro 名

我曾怀疑 `markerId` 是 `OutroNN` 的编码。**实测否定：**

- 197 个不同 markerId 中，只有 **14 个**跨赛道重复
- 那 14 个在 triggers.md 里对应**互相矛盾的名字**

例：
```
id 2005: {'Outro01', 'Outro04'}
id 1723: {'Outro06', 'Outro04'}
id 1969: {'Outro05', 'Outro02'}
```

**结论：`markerId` 是逐记录的唯一身份，不是名字编码。**

## 6. 旧研究 JSON 的命名与 triggers.md 不一致

拿 `MKW_BGM_30赛道统一结构化数据_v2.json` 的 `exit_cues[].name` 与 `triggers.md` 对比：

```
agree=38  disagree=127
```

**165 条可比记录里，127 条名字对不上。** 例：

| 赛道 | 位置 | 旧研究说 | triggers.md 说 |
|---|---|---|---|
| FirstCircuit | 289909 | Outro00 | **Outro01** |
| WestCity | 905625 | Outro02 | **Outro00** |
| Coaster | 637714 | Outro00 | **Outro01** |

**但这份对比不能判定谁对** —— 两者都是分析产物。它只证明：**「Outro 名 ↔ 位置」的绑定在现有分析材料里本身就不一致，不能作为可靠依据。**

→ 旧研究把位置按升序直接编号了，**没有真正的名字绑定**。这正是交接包 `docs/00` 说「旧文档不能覆盖现行实现」的具体体现。

## 7. 位置顺序：按 index 严格升序

62 个多标记表中，**全部**满足 `position[0] < position[1] < ...`。

但发现一个真实数据异常：`BGM_Stage_DinoDinoJungle` 有**重复记录**（idx=0 和 idx=1 同为 id=2049 pos=420438）。这是原始数据里的重复，**不是解析错误**，记录下来不擅自去重。

> **不能把任何一份的名字绑定当成已确认事实写进产品。**

正确的做法是：UI 和播放器把 marker 位置当作**位置信息**使用，把 `OutroNN` 名字标为 `UNVERIFIED`，直到有真正的 L3 证据（游戏内实测或官方文档）。
