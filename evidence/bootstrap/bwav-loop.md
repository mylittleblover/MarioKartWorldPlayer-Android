# BWAV Loop 元数据验证（VER-02 前置）

- **checked_at**: 2026-11-07T21:35+08:00 (Asia/Shanghai)
- **证据级别**: **L1（元数据）** —— 字段位置与取值一致性已核实；**不是 L2 听音验证**
- **数据**: 20,991 个 `.bwav` 全部逐个读头，只读

---

## 结论：**原始 BWAV 里确实有 loop 点，就在头部 +76 / +80**

这是本轮最重要的发现 —— 之前担心的「`.wav` 没有 `smpl` chunk 导致 loop 信息丢失」**不成立**，因为 loop 点在**原始 bwav 的头部**里，从未丢失。

## 1. 字段布局（实测）


## 3. 关键规律：**有 loop 时 `loopEnd` 恒等于总帧数**

对全部 174 个带 loop 的音乐文件：

```
loopEnd == frames : 174
loopEnd != frames : 0
```

也就是说 **BWAV 的 loop 永远是「从某点循环到结尾」**，不存在「中段循环」。这一点对播放器实现是决定性的：不需要支持任意区间循环，只需要 `[loopStart, frames)`。

## 4. 音乐文件的 loop 实例

| 文件 | 总帧数 | loopStart | 循环长度 |
|---|---|---|---|
| `BGM_Stage_Coaster` | 3,373,711 | 493,714 | **60.000 s** |
| `BGM_Stage_Coaster_Pre` | 2,427,426 | 452,571 | 41.143 s |
| `BGM_Stage_Coaster_Fast` | 2,880,800 | 422,268 | 51.219 s |
| `BGM_Stage_Coaster_Outro00` | 226,286 | **无 loop** | — |
| `BGM_Stage_Coaster_Bridge` | 88,320 | **无 loop** | — |
| `BGM_Stage_PeachBeach` | 3,571,200 | 622,080 | 61.440 s |
| `BGM_Rainbow_Area1_Bridge` | 291,646 | **无 loop** | — |
| `Dm_RainbowAppears` | 3,483,690 | **无 loop** | — |

**语义完全自洽**：
- 主题曲 / Pre / Fast 有 loop（要循环播放）
- **Outro 没有 loop**（播完就结束，不该循环）
- **Bridge 没有 loop**（过渡段，一次性）
- **Dm_ 过场曲没有 loop**（演出配乐，不循环）

这不是巧合 —— 字段语义与音乐功能一一对应。

## 5. 附带发现：BWAV 体数据是 DSP-ADPCM 压缩

`(size - 32) / frames / channels ≈ 0.5714 = 8/14`，即每个通道每 14 个采样占 8 字节 —— 这是 **Nintendo DSP-ADPCM** 的教科书比例。

我尝试写了 DSP 解码器去跟已解码 WAV 对比，**没有对上**（首样本解码结果为 0，参考为 1471）。可能原因：块内声道交织顺序、头部元数据长度可变（实测 80/112/120/128 字节不等）、或块头系数表不同。

**结论：DSP 解码 = UNRESOLVED。** 但这**不影响 loop 点** —— loop 帧号是明写在头部的，与是否解码无关。

> 换句话说：**VER-02 可行**（loop 有数据依据），但要真正"听"到音频，还需要能解码 DSP 的工具。而 `readable_assets` 里已有的 20,991 个 wav 就是官方/工具解出来的，可以直接用。

## 6. 对 VER-02 / 播放器的影响

1. **loop 点不需要逆向** —— 直接读 `+76` / `+80`
2. **loop 只有「到结尾」一种形态** —— 实现简单
3. **无 loop 用 `0xFFFFFFFF` 哨兵** —— 必须显式处理，不能当 0 或无符号最大值参与运算
4. **loopStart 是源采样帧，不是 Transport 帧** —— 与 `docs/02` 的时间坐标要求一致
5. 仍**未验证**：loop 点是否与听感吻合（L2）、是否与原版游戏行为一致（L3）
