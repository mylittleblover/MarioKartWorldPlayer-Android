# アーキテクチャ

[简体中文](ARCHITECTURE.md) | [繁體中文](ARCHITECTURE.zh-Hant.md) | [English](ARCHITECTURE.en.md) | **日本語**

このドキュメントは、**なぜこのようにレイヤーを分割したのか**、そして各レイヤーがそれぞれ何を拒否するのかを説明します。

コードを見れば「どうなっているか」は分かりますが、「なぜ別のやり方にしなかったのか」は分かりません。このプロジェクトにおける決定の大半は、一見自然に見えるもののサイレントな不具合を招く選択肢を排除した上で下されています——その排除理由を書き残しておかなければ、次の人が「つい元に戻してしまう」からです。

## 2. エンジン所有権がプロセス単位にある理由

**失敗する形**：`AudioEngine` を `PlayerViewModel` の中に置く（最も自然な書き方）と、画面を離れたときに
`onCleared` が発火してエンジンが破棄され、音楽が止まってしまいます。音楽プレーヤーとしてこれは許容できません。

**制約**：フォアグラウンドサービスは lifecycle スコープのオブジェクトを所有できません。サービスは OS によって再生成される可能性があり、Activity は繰り返し破棄・再生成され得ます。

**結論**：エンジンは `PlaybackHolder`（プロセス単位のシングルトン）に帰属し、サービスと UI の双方がそこから同一の `PlaybackSession` を参照します。

```
PlaybackHolder.get()  ──> PlaybackSession（唯一）
                              ├── PlaybackService  フォアグラウンド／通知／MediaSession を提供
                              └── PlayerViewModel  状態の読み取り・コマンド送信のみ
```

**サービスは音声状態を一切保持しません**。サービス側にもう 1 つトランスポート状態を再実装することは、プレーヤーに「2 つの時計が存在し、通知表示と実際に聴こえる音が食い違う」現象が起きる典型的な原因です。

`PlayerViewModel.onCleared()` は現在**意図的に再生を停止しません** —— ポーリングのキャンセルのみを行います。ここが唯一「ライフサイクル終了時にクリーンアップしない」箇所であり、コメントにその理由を明記しています。

## 3. `AudioOutput` をモック化できない理由

`AudioOutput` は private コンストラクタを持ち、ネイティブハンドルをラップしているため、テスト内でテストダブルに差し替えることが**できません**。

これは見落としではなく、次の認識に基づく判断です：

| テスト層 | カバーできる範囲 | カバーできない範囲 |
|---|---|---|
| JVM | セッション自身の状態管理・所有権・失敗時のクリーンアップ | 実際のストリーム開始 |
| 実機 | 実際の Oboe ストリーム・コールバック回数・タイミングパケット | 人間の耳による聴感 |

そのため `PlaybackSessionTest` では `openOutput = { _, _ -> null }`（すなわち「音声デバイスなし」状態）でセッションロジックをテストし、
実際のストリーム開始は `AudioOutputDeviceTest` に委ねています。

**テストカバレッジを稼ぐために `AudioOutput` へ注入可能な偽インターフェースを追加することはしませんでした** —— それでは偽インターフェースをテストしているだけで、実際の経路をテストしたことにならないからです。

## 4. デコーダの修正は 2 箇所のみだが、いずれも致命的な不具合

`engine/native/decoder/BwavFormat.hpp` は 2 箇所修正されています。根拠はドキュメントではなく MKW の実ファイルです：

### 4.1 最終ブロックの切り詰め

MKW は**最終チャンネルの最終ブロック**を必要な分だけに切り詰めます：

```
minimum = (blocks - 1) * 8 + 1 + ceil(lastSamples / 2)
```

元のパーサは完全な 8 バイトブロックを要求していたため → **5,694 ファイルが拒否**されていました。

### 4.2 予測器シード

元のパーサは `u16(header+68) == u8(firstByte)` を要求していました。実測では **654 ファイル**がこれを満たしません
（`BGM_Stage_Coaster.bwav`：ヘッダ記載は 39、先頭バイトは 53）。

`<= 0x7f` のみを要求するように変更しました。

**この 1 箇所はどのリファレンスデコーダでも検証されておらず**、理由は「こう直さないと再生できない」のみです。最もリスクが高いため、次の対策をとっています：

- 自動検証：`dsp_verify.py`（独立した第 2 実装）でサンプル単位に照合し、5 曲・52,000 サンプルで maxdiff = 0
- 手動検証：実機試聴により**音程が正しい**ことを確認（シードが誤っていると DSP-ADPCM の予測が狂い、耳で判別できるほど音程が崩れます）

2 系統の独立した証拠が同時に成立して初めて、この修正は正しいと言えます。

## 5. ステータスコードは必ず名前で表示し、強制変換しない

`AudioStatusText` は `EngineStatus` 0..11 と `SourceStatus` 0..14 のすべてに名前を付けており、`UNKNOWN(n)` が
`Ok` に強制変換されることは**決して**ありません。

**理由**：ステータスコードは数値が大きく重複しているため（0 = Ok、1 = InvalidRequest、7 = OutputActive…）、
誤った強制変換 1 つで手元の失敗が成功として表示されてしまいます。本プロジェクトでは「音声を確認せずステータスコードだけを見た」ことによる誤判定がすでに 2 回起きています。

---

## 6. グラフエンベロープはネイティブ呼び出し前に検査する

`GraphProbe` は `AudioEngine.loadGraph` の前に magic、バージョン、body 長、CRC32 を検証します。

**理由**：ネイティブ側に不正なパケットが渡ると「エラーコードを返す」のではなく未定義動作になるためです。検証を Kotlin 側に置くことで、壊れたパケットが JNI を越えること自体を防ぎます。

`GraphBuilder` と `GraphProbe` の双方で、不正なパス、範囲外の値、不正なサンプルレートを拒否します。

## 7. シークの挙動は 2 層間で**意図的に異なる**

| 層 | 範囲外入力の扱い | 理由 |
|---|---|---|
| `SeekTarget`（UI 側） | **クランプ** | ドラッグ操作では NaN、±∞、負数が生じ得るため、クランプでシークバーの操作感を保つ |
| `PlaybackController` | **拒否してエラー** | ここまで範囲外の値が届くのは上流のバグであり、必ず表面化させる必要がある |

テストでは範囲外シーク時に `engine.seekCalls == 0` をアサートしており、**範囲外リクエストはネイティブ層へ一切入りません**。

**もし両方の層でクランプしてしまうと、上流のバグが永久に隠蔽されてしまいます。**

## 8. `playing` と `loaded` は別の概念

エンジンの `Play` は**コマンドキュー**を経由するため、同じ瞬間にスナップショットを取得してもまだ `Stopped` のままの場合があります。

- `playing`：エンジンスナップショットが再生中と報告している（一時停止できるかの判定に使用）
- `loaded`：`Play` が受理済みである（フォアグラウンドサービスを維持すべきかの判定に使用）
- `active = playing || paused || loaded`

**混同すると破綻する**：初期版では `playing` をサービス維持のガードに使っていたため、読み込み成功直後にサービスが即座に起動を拒否する不具合が起きました（`PlaybackService.start()` が false を返す）。

## 9. スナップショットのバージョン不一致時は必ず null を返す

`EngineSnapshot` と `TimingDiagnosis` はどちらも wire version（スナップショット 8、タイミング 1）を検査し、一致しない場合は `null` を返します。

**理由**：オフセットの読み違いはクラッシュせず、「再生していない」を「再生中」、「不健全」を「健全」と誤表示するだけです。
これこそ本プロジェクトで最もコストの高いバグの種類——サイレントに起きるからです。

---

## 10. タイミングデータは診断専用であり、スケジューリングを駆動しない

`CallbackTiming` は各コールバックの CPU / wall 時間を記録し（2048 スロットのロックフリーリングバッファ）、
`TimingDiagnosis` がそれを `HEALTHY` / `DEGRADED` / `FAILING` / `NO_DATA` に判定します。

**いかなる再生判断にも関与しません。** ヘッダファイルのコメントにも「Never drives Transport or musical scheduling」と明記されています。

**理由**：タイミングがスケジューリングに影響を与えられるようになると、計測自体が干渉源となり、「音飛び」と「音楽ロジックのバグ」が互いを覆い隠してしまいます。

判定しきい値（フレーム落ち 1% / 5%、予算 70% / 90%）は実測値ではなく**ポリシー**であり、定数として記述しテストで固定しています。

## 11. codec 2 は推測しない

253 ファイル（JukeBox 227 + Cutscene 22）が codec 2 を使用しています。

**確定していること**（253/253 ファイル、594 チャンネル、例外なし）：

```
u32 tag 0x80000001, size 24   ← 6 つの u32 設定、全ライブラリで共通：256 48000 32 0 0 120
u32 tag 0x80000004, size N    ← エンコード済み音声
```

**確定していないこと**：パケット境界。`tools/k2_framing.py` でサイズプレフィックス 1/2/3/4 バイト × ビッグ/リトルエンディアン ×
アライメント 1/16/64 × 開始オフセット 0..4095 を総当たり検証しましたが、**ペイロードを過不足なく消費できたものは 1 つもありませんでした**。

平均ビットレートは 0.2177 バイト/サンプル（83.6 kbps）で一定しており、250 万〜1,550 万サンプルにわたって変動は 0.08% 未満です——
ターゲットビットレート符号化（Opus 等）の特徴を示していますが、パケット境界が分からなければデコーダに渡せるものがありません。

**推測しない理由**：仮に音が出る実装を書けたとしても、それが正しいと証明するリファレンスが存在しません。引き継ぎルールには
`never guessing` と明記されています。**「再生できそうに見える」ことと「確かに正しい」ことは別物であり、後者を検証できない状況では前者に価値はありません。**

UI には漠然とした unsupported ではなく `BWAV codec 2 (chunked, 83.6 kbps at 48000 Hz)` と表示します——
「何であるか」を知ることと「どうデコードするか」を知ることは、別の成果です。

## 12. カタログは自身の免責事項を保持する

`app/src/main/assets/catalog.json` は `tools/gen_catalog.py` で生成され、カバレッジ宣言を**そのまま保持**します：

```json
"freezeStatus": "PROVISIONAL_INCOMPLETE",
"coverage": "INCOMPLETE",
"coverageReasons": ["only 4/499 archives read", "verification not performed: ..."]
```

UI はこれらの行を**そのまま表示します**。

**理由**：650 件を完全なサウンドトラックであるかのように表現するのは、**取り消せない虚偽の表明**になります——ユーザーは件数を数えませんし、
欠落している 495 個のアーカイブ内の楽曲はリストに一切現れず、ユーザーは「ゲームに入っている曲はこれだけだ」と思い込んでしまいます。

`Catalog.isPartial` は `freezeStatus != "FROZEN" || coverage != "COMPLETE"` で判定され、テストで固定されています。

## 13. 永続化：破損ファイルは削除せず隔離する

`LibraryStore` は `filesDir/library.json` を書き込みます：

- アトミック置換には `File.renameTo` ではなく `Files.move(REPLACE_EXISTING)` を使用します
  （`renameTo` は Windows 上で既存ターゲットを上書きしないため、2 回目の保存がサイレントに失敗します）
- 解析失敗またはバージョン不一致 → `.corrupt` にリネームして**保持**し、表示可能な理由を返します
- フィールドが欠落している行はデフォルトで `playable = false` とします（情報欠落時は無理に再生させない）

**削除しない理由**：削除してしまうとユーザーの楽曲ライブラリが痕跡もなく永久に失われるからです。

## 14. テストをこの階層に分ける理由

| 層 | 件数 | この層に置く理由 |
|---|---|---|
| Python | 143 | 全ライブラリ統計（20,991 個の bwav）、サンプル単位の照合、コンテナ総当たり探索 |
| Kotlin JVM | 242 | 純粋ロジック：状態機械、算術、解析、永続化。**高速で Windows でも動作する**ため、`renameTo` のプラットフォーム差異を捕捉できた |
| Android Instrumentation | 69 | 実際の Context / ネイティブライブラリ / Oboe / アセットが必要 |
| 手動（S6） | 1 | 聴感。**自動化不可能** |

**試聴による証拠と自動テストによる証拠は分けて記録します**。前者は再現不能であり報告者の判断に依存するためです。両者を混ぜてしまうと、後から見てどの結論が機械によるものでどれが人によるものか区別できなくなります。

## 15. 既知のアーキテクチャ上のトレードオフ

`PlayerViewModel.prepared` はダイジェストをキーにして**メモリ上**に保持されています（`mutableMapOf<String, Prepared>`）。
OS によってプロセスがキルされた後、永続化から復元されるのは名前とメタデータのみであり、**音声バイト列はファイルの再選択が必要**です。

`select()` がこの状態の行に出会うと、`Not prepared / Pick this file again to reopen it` を表示します。

**これは意図的なトレードオフです**：3 MB × N の音声バイト列を永続化するとストレージ使用量が大きく膨張する一方、ファイルの再選択は許容できるコストだからです。
将来これを変更する場合は、`library.json` にバイト列を詰め込むのではなく、`AudioPicker` のキャッシュ戦略側で変更すべきです。
